# 角色资产流水线（Qwen-Image 2.1）

把「一版服装的一张照片」变成**可复用角色资产**的流水线。三段资产各自只负责一件事，混着做就会互相打架。

| 资产 | 职责 | 产出 | 提示词文件 |
|---|---|---|---|
| ① 服装模板 / 服装板 | 只要衣服，不要人 | 幽灵人台单品展示图 / 多格服装板 | `references/01-garment-template.md`、`references/02-garment-board.md` |
| ② 面部特写人像 | 只要脸与头发 | 身份参考图（头肩以上、脸大） | `references/03-face-portrait.md` |
| ③ 四视图角色版 | 把 ①②合成四格标准表 | 正面/背面/侧面全身（无头）+ 第 4 格大脸 | `references/04-four-panel-sheet.md` |

派生规则（换一版服装要改哪几处）见 `references/05-derivation-rules.md`；参数、接线、踩过的坑见 `references/06-params-and-pitfalls.md`。要「白模 + 服装板 → 真人全身 → 换脸」时**不要另写模板**，直接走技能 `comfyui-face-swap:references/two-stage-garment-to-body.md`（已含 V1–V7 变量、I1–I10 不变量、脸像素门槛、尺寸掉档与补痣排查）。

## When to Use / 何时用

- 用户给一张服装照/上身照，要「空镜服装模板」「幽灵人台展示图」「服装板」。
- 用户要建或更新角色参考表（四格/三格：站立格无头 + 一格大脸）。
- 用户按新服装更新已有角色表，问「这版提示词要改哪里」。
- 用户在做 MiniMax H3 参考图生视频，需要上游身份图/服装图/场景图。

## 两套格式，绝不混用

| 任务 | 规则 | 写法 |
|---|---|---|
| **文生图**（场景静帧、面部人像） | Qwen T2I 规则 | **一段到底的观察者描述**：开篇约 20 词锚句（`The image is a ⟨vertical⟩ ⟨style⟩ ⟨photograph⟩ of ⟨subject⟩, ⟨background⟩.`）、8–14 个位置短语、光单独一句、结尾一句整体构图；**不用标签、不用祈使句、不写比例数字** |
| **图编辑**（服装模板、服装板、四视图） | Qwen Edit 规则 | **以动作开头的一段指令**：`<image1>`/`<image2>`… 分工明确、指明画布、**肯定陈述**；**要改的写细、要留的写粗**（一句总括保留句）；单段无换行 |

把「编辑式标签清单」塞进 T2I、或把「观察者长描述」塞进编辑，都会掉效果——这是最容易犯的格式错。

## 十条铁律

1. **一个资产只干一件事**：服装图里没有人；人像图不展示服装；角色表身份只来自人像图。
2. **能指图就不写字**：身份/服装一律「见 `<imageN>`」；用文字复述五官或衣料会让模型**重画并降低相似度**。**唯一例外：既无 LoRA 也无参考图时**，五官必须逐项写全（脸型 / 眉 / 眼 / 鼻 / 唇 / 唇色）—— 不写就是把脸交给模型的默认审美，出来的是「同类型的好看脸」，不是指定的人。

   反过来同样成立：**手上没有服装图时，不许写出带具体领型 / 闭合方式 / 颜色 / 工艺点的服装段。** 只能给槽位（`[TOP: …]`, `[GARMENT: …]`）和骨架，并明说缺哪张图。按口述猜出来的服装段，模型会把它当真实设计照画，错在细节上而且错得不显眼（多一个口袋、换一种领口都算）；用户下一句必然是「我的图都没发给你，你怎么写提示词」。服装段永远从 `<image3>` 那张服装台图反推。
3. **要保留的写粗，要改的写细**：把保留物逐项描述＝给模型下达「重画」指令。
4. **负向里绝不能出现正向要求的东西**（正向要「裁在肩线」，负向就不能留 `cropped full body`）。
5. **LoRA 只插在真正用权重造脸的那一步**：人像模块可插；服装板/服装模板**不插**；四视图**不插**（身份走 `<image2>`）。
6. **选对 LoRA 文件**：读 safetensors 元数据确认 `ss_base_model_version` 与触发词——同名 LoRA 常分属 zimage/krea2/sdxl/qwen，挂错基座等于没挂。
7. **裁剪/对齐这类「分寸」问题一律量像素**，不采信肉眼或看图工具的定性描述。
8. **服装颜色必须点名**（`mid-grey` 要写「不是黑也不是白」），否则灰会塌成黑；同时给足画幅像素。
9. **一张图只能有一种身份**：定义内容用 `<Subject N>`/`<imageN>`，当帧锚才谈「首帧」，不能兼两职。
10. **画幅与像素开工前核对**：编辑类模块 `custom_size=false` 时输出尺寸**跟随第 1 张输入图**；参考图比例与目标比例不一致，模型会重新构图。

11. **已跑通的流水线只许「最小替换」。** 换一版服装＝只改三处：**服装名词段 + 颜色保真句 + 负向里的服装词**。骨架句、取景句、结构句、触发词写法、负向的非服装部分**一个字都不许动**。三块模板（`02`/`03`/`04`）在同 IP、同资产内是**冻结原文**，改坏过：把服装板的「三整装 + 细节格」改写成「竖排单品」→ 服装不再分解（只出一张平铺图）；把人像的触发词从锚句主语改成独立首行 → 脸变通用。**但「冻结」有边界**：用户要求换 IP／换风格／新建人物时，按骨架重写对应段落（见 `references/03-face-portrait.md` 的三段旋钮与仓九段骨架），不是拒绝、也不是只改一个词。
12. **改之前先备份，改坏了按节点 diff 回滚。** 动提示词前先把「当前可用版本」导出成 API 格式 json（子图被摊平，能逐节点比）。出问题时先 diff：若两版差异**只有提示词**，就是提示词的锅——**不要去怀疑种子/开关/LoRA/比例**；然后只回滚提示词，其余参数原样保留。没有 baseline 就不许在提示词上迭代。
13. **交付前把用户点名的条目逐条勾出来。** 他提三条就列三条，做到的打 ✅、没做到当场说。**「其他不变」不等于「什么都别动」** —— 它通常意味着「除了我点的那处，其余保持上一版字面」，所以改完要拿上一版原文对一遍：只允许被点名的字段不同。一次只改一个变量（发型/表情/皮肤/背景/服装同时动两个，出问题分不清是谁的锅）。
14. **「固化」＝交出骨架＋三分类，不是把字符串锁死。** 一次固化必须给出四样：① 骨架（槽位化句式，`{{}}` 可填）② 变量表（换 IP／换风格／换服装时允许改的那几项）③ 不变量（逐字保留的几条，写明为什么）④ **真正决定画面的 2–3 句**（只有改这几句才换人／换款，改其余只是调气质）。用户说「固化」是「以后照结构会写」；交一段「冻结原文」会被打回——他要复用，不要复读。
15. **分清硬约束与软约束，别为软约束反复调词。** 硬约束（下装腿型、裤长、三色分离、画面里有没有人、脸占多大）一句话就能锁，写死即可；软约束（腰位中↔高、上装贴身↔宽松、皮肤质感、面料织法）**写死也会漂 ±1 档** —— 先如实告诉用户「这里会漂、你要哪一档」，要精确只能靠后续局部编辑或换光，不要在提示词上磨。把软约束当硬约束反复重写，是这类活最烧时间的坑。

16. **用户点名「调用某技能」＝字面执行：第一步 `skill_view` 把该技能和对应 references 读进来，再动手。** 凭会话记忆重写已验证原文，必然把技能里明令禁止的写法重新犯一遍（markdown 反引号包住锚点 token、往身份句里塞 `skin condition` / `expression`、服装段里写 `tee-dress` / `falls from the shoulders`）。开工先问一句：这条线有没有固化页？有就先读，再决定改哪个槽；用户看到「说了调用却没调用」会直接失去耐心。

17. **基准先钉来源，再谈「逐字一致」；对不上先怀疑比错了样本。** 任何标着「冻结原文／逐字一致」的段落，页头必须写死三样：**产出文件名 + 词数/字符数 + 归一化 sha256**（外加尺寸与采样参数）。没有这三样，谁都无法复算，审计只能靠关键词猜服装 —— 猜「格子裙」就漏掉「百褶裙 + 领口格纹」，最后把有背书的基准判成「无产出背书」。交付前量三个数：① 与基准产出内嵌 `prompt` chunk 的相似度 ② 用户点名要改的槽之外是否逐字相同 ③ 锚点 token 是否裸写（反引号 0 处）。相似度对不上时**先换比对对象**（同服装才可比），再下结论：实战里「334 词 vs 367 词、0.756」不是基准假，而是拿另一套服装的产出来比；正确的同服装对照是 1.000。命令：`python scripts/verify_prompt_drift.py baseline.txt candidate.txt --slot "START:::END" --ban "tee-dress"`；三项任一不过就不许交付（相似度 <0.90 / 槽外有改动 / 有反引号 token），并把这三个数一并发给用户，代替「我保证没动别处」。

18. **先认产物，再写提示词。** 用户丢一张图说「换成这一版」时，先确认它是**单张幽灵台**（一件衣服悬空 + 鞋，整幅无分格）还是**多视角服装板**（正/背/侧三视图 + 细节格，有分格边框）。两者都能当 `<image3>`，但走法不同：单张幽灵台**不需要先跑服装板**，直接把它接进 `<image3>` 即可；把它叫成「服装板」并按多视角去描述，会让用户以为你在说另一件东西。判据就一条：这幅图里有没有同一件衣服的多个角度。拿不准先问一句。

19. **无头格成不成，看服装形态，不看提示词。** **两件式（上衣止于腰 + 独立下装）稳定出无头；一件式连身裙是概率事件** —— 同一份 386 词、同一 seed 会一次成一次败。所以连身裙冒头时：**不许再改骨架句、不许再做措辞实验**（已经证明清干净的版本照样冒），同 seed 跑 3–5 张挑一张，或把连身裙改写成「同色上衣 + 同色下装」两件式描述再跑。同样**不许用后期裁切/铺背景去救**：模型把头发画到肩线以下，任何水平裁切都会留半截（三种修法实测全废，见 `references/04-four-panel-sheet.md`）。

## 库的组织与验收约定（用户定的规矩）

- **模板 / 案例分离**：提示词资料一律按「通用骨架」组织 —— `templates/` 只放**结构与变量位**（`<场景卡>` `<人物卡>` `<服装卡>` `<一个事件>` `<一个情绪走向>` 这类占位），`cases/` 放某一次的具体记录。**案例内容不得写进模板正文**：能提炼成变量的才进模板，只能提炼成「这次就是这样」的留在案例里。
- **四态标记**：✅ 已验证（有文件名 / 元数据 / 尺寸这类硬证据）｜🗄️ 暂定存档｜⚠️ 未验证｜⛔ 弃用。多写法并存时，**没赢的那一版标「暂定存档」并写明适用场景，不许删** —— 换个题材或运镜它可能更优。比较两式**必须锁 seed**，否则不算对照。
- **不为证明小事花卡**：重量级链路（六图编辑、多次重跑）维持现状；结论不足宁可如实标「未受控（C 级）」，不要反复要重跑。
- **登记**：每条结论记「参数指纹 + 正负向原文 + 文件真名 + 尺寸」，否则下次无法复算。
- **复审＝拿产物元数据 diff 文档。** 改过模板或规格之后，模块表与「未验证清单」会立刻过时。复审时逐条读 PNG 内嵌 prompt（尺寸 / LoRA / 提示词头），与文档对照：把「样本为零」翻成已闭环、把工作流上挂错的 LoRA 或误跑的尺寸登记成待办。一条命令：`python scripts/check_output_meta.py <output_dir> --glob '*.png' --last 12`（用 ComfyUI 的 venv 解释器，PIL 在那边）。要判「模板与样本是否同一份（全文 vs 骨架相似度）」「跨步骤掉色（ΔE/色相而不是 ΔRGB）」「换头有没有动衣服（同尺寸对齐后的分带差）」，走技能 `comfyui-output-verification`，它自带 `comfyui-output-verification:scripts/audit_outputs.py`。

## 最小交付物

对一版新服装，交付三样即可开工：① 服装模板正向+负向 ② 人像正向+负向 ③ 四视图正向+负向。全部**整段可粘贴**，不给「改哪几句」的 diff。

**一次只给一个产物 —— 除非他一次点名了几份。** 他只问一句，就回一段提示词 + 一句判据；他一次点名要「服装模块 + 角色模块」，就在**同一条回复里把两份都给全**（各自标明槽位与参数），不许拆成两条、不许只给一份再解释、不许用「改哪几句」的 diff 代替成品。判据卡、词库表、方案对比、失败模式表是写给我们自己看的，堆进回复里会被当成「把简单问题复杂化」；他要展开再展开。
